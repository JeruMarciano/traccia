## 1. `chromiumoxide` 0.7 — pinned, and what it will and will not do

### The pin

`chromiumoxide = { version = "0.7", default-features = false, features = ["tokio-runtime"] }`

resolves to exactly **0.7.0**. That is the only release in the `0.7.x` range; the crate's published
versions run `…0.6.0, 0.7.0, 0.8.0, 0.9.0, 0.9.1`. 0.9.1 is current. The plan named 0.7 and 0.7 is
what is pinned — but a reader should know that this pin is two minor versions behind, and that
0.9's feature set differs (no `tokio-runtime`; `default = [bytes]` rather than
`[async-std-runtime, bytes]`). Whether to move to 0.9 is a Phase 2 question, not this task's.

`default-features = false` matters: 0.7.0's default pulls `async-std`. With only `tokio-runtime`,
the async-std stack stays out.

### Method

Read the crate source at
`~/.cargo/registry/src/index.crates.io-*/chromiumoxide-0.7.0/`, then compile-checked every claim
below with a temporary probe module inside `src-tauri` that was deleted before commit. Claims that
rest on a compiler error name the error.

### Can the crate send raw CDP commands at all?

**Yes.** The task's stop condition is not met.

- `chromiumoxide::cdp` re-exports the whole generated protocol (`chromiumoxide_cdp`). Every CDP
  command has a typed params struct.
- `Page::execute<T: Command>` (`src/page.rs:186`) and `Browser::execute<T: Command>`
  (`src/browser.rs:422`) send any of them.
- `chromiumoxide::conn::Connection` is public, as is
  `Connection::submit_command(method, Option<SessionId>, params)` (`src/conn.rs:77`) — the only
  public API in the crate that can address an **arbitrary** session.

### Behaviour 1 — `Target.setAutoAttach` with `flatten: true`, reapplied in every new session

**Available, and both ways.**

- **High-level, automatic.** `Target::page_init_commands` (`src/handler/target.rs:571`) issues
  `SetAutoAttachParams` with `.flatten(true).auto_attach(true).wait_for_debugger_on_start(true)`
  as part of every tracked target's init chain. The handler also enables `Target.setDiscoverTargets`
  at construction (`src/handler/mod.rs:96`), so targets are discovered.
- **Raw.** `chromiumoxide::cdp::browser_protocol::target::SetAutoAttachParams` builds the same
  command and `Page::execute` sends it. Compile-verified.

One caveat on "reapplied recursively in **every** new session". The init chain runs per `Target`,
and a `Target` is created only from `Target.targetCreated` (`on_target_created`,
`src/handler/mod.rs:424`). `on_attached_to_target` (`:448`) does **not** create one — it binds a
session to a `Target` that already exists and otherwise records an orphan session. So the recursion
is the browser's, driven by `setDiscoverTargets`, not something the crate re-drives per attach.
That is probably fine, but it is not the same guarantee the spike stated, and Task 7 should assert
it rather than assume it.

### Behaviour 2 — arm `Fetch`/`Network` in the new session **before** `Runtime.runIfWaitingForDebugger`

**Not available through `Browser` at all — neither high-level nor raw.** This is the finding that
matters.

`Target::on_event` (`src/handler/target.rs:258–268`) handles `Target.attachedToTarget` like this:

```rust
CdpEvent::TargetAttachedToTarget(ev) => {
    if ev.waiting_for_debugger {
        let runtime_cmd = RunIfWaitingForDebuggerParams::default();
        self.queued_events.push_back(TargetEvent::Request(Request {
            method: runtime_cmd.identifier(),
            session_id: Some(ev.session_id.clone().into()),
            params: serde_json::to_value(runtime_cmd).unwrap(),
        }));
    }
```

The child session is resumed **immediately and unconditionally**, with nothing armed in it. That is
precisely the startup race F2 exists to close, and F2's twenty cold starts with zero escapes were
obtained by doing the opposite. There is no hook, config flag or callback between the two.

Nor can the arming be raced from outside:

- `Browser::execute` hardcodes `session_id: None` (`CommandMessage::new`, `src/cmd.rs:48`), so it
  can only address the browser session.
- `Page::execute` addresses that page's own session, and a `Page` exists only after its target has
  finished initialising — after the resume.
- `CommandMessage::with_session` (`src/cmd.rs:62`) is the right shape, but `mod cmd` is
  `pub(crate)` (`src/lib.rs:82`). Confirmed by rustc: **E0603, "module `cmd` is private"**. And the
  channel that would carry it, `HandlerMessage`, is `pub(crate)` too (`src/handler/mod.rs:746`).

The only public route to an arbitrary session is `conn::Connection::submit_command` — which means
opening a second WebSocket and driving the protocol directly, i.e. **not using `Browser`/`Handler`
at all**. That is hand-rolled CDP wearing chromiumoxide's generated types.

### What Task 7 should take from this

The crate is fit as a **typed CDP vocabulary** and unfit as an **interception loop owner**. Task 7
should use `chromiumoxide::cdp` for the protocol types and `chromiumoxide::conn::Connection` (or
`tokio-tungstenite` as the spike did) for the transport, and must not delegate the attach/resume
sequence to `Browser`. This is the same conclusion the CDP spike reached for a different reason —
it recorded chromiumoxide as *avoided*, "which would own the interception loop the egress guard
must own." That judgement holds, and now has a mechanism behind it.

Note also, for the record, that under-arming here fails in the dangerous direction the spike named:
a missed vendor is silently absent from the map rather than visibly uncertain.

### An unbudgeted dependency

`chromiumoxide` 0.7.0 depends on **`reqwest`** unconditionally — `default-features = false`, so no
TLS backend and no `h2`, but it pulls `hyper`, `hyper-util`, `tower` and `tower-http` into the
tree. `src-tauri/Cargo.toml`'s dependency budget says of exactly these crates: "Deliberately NOT
taken." The `Cargo.toml` comment has been amended rather than left to contradict the tree.

It is used in one place: `Browser::connect_with_config` (`src/browser.rs:100`) fetching
`/json/version` over HTTP when the URL is `http`. That is the call this project already avoids by
reading `DevToolsActivePort` out of the browser's own profile. So the code is reachable only if
Phase 2 calls `Browser::connect`; §2 measures what that reachability costs.

Two things follow, neither decided here. The HTTP stack is compiled in whether or not it is called,
which is surface area in an app whose whole claim is that it makes no outbound request. And the
call site does `req.remote_addr().unwrap()` — a third-party `unwrap` on a network path, which the
project's own rules forbid in its own boundary modules.

## 2. What `chromiumoxide` costs in shipped bytes

### Method

Same as `docs/decisions/2026-07-31-tauri-bundle-measurement.md`, so the delta is meaningful:

```bash
source "$HOME/.cargo/env"
npm run tauri build
find src-tauri/target/release/bundle -name '*.dmg' -exec stat -f '%z %N' {} \;
stat -f '%z %N' src-tauri/target/release/traccia
```

Baseline is that document's figures: `.dmg` **1,536,327**, binary **2,436,064**.

### The measurement trap, stated because it nearly produced a wrong number

Declaring the dependency and building gives **+160 bytes of binary**. That number is a lie. The
release profile is `lto = true`, `opt-level = "z"`, `codegen-units = 1`, and nothing in the crate
referenced chromiumoxide, so the linker discarded all of it. Making the probe module `pub` in the
library was not enough either — the final executable's LTO strips anything unreachable from
`main`. Only after the probe was called from inside `run()` did the real cost appear.

Anyone re-measuring a not-yet-used dependency in this repository will hit the same trap.

### The numbers

| Build | Binary | Δ binary | `.dmg` | Δ `.dmg` |
|---|---|---|---|---|
| Baseline (2026-07-31, no chromiumoxide) | 2,436,064 | — | 1,536,327 | — |
| Declared, never referenced | 2,436,224 | **+160** | 1,539,798 | +3,471 |
| Referenced but unreachable from `main` | 2,452,816 | +16,752 | 1,542,207 | +5,880 |
| **Reachable, without `Browser::connect`** | **3,816,800** | **+1,380,736** | **2,254,737** | **+718,410** |
| **Reachable, with `Browser::connect`** | **4,017,280** | **+1,581,216** | **2,372,693** | **+836,366** |

`Browser::connect` — and therefore the reqwest/hyper/tower stack — accounts for **200,480 bytes of
binary** and **117,956 bytes of `.dmg`** of that. Avoiding that one call is worth about 115 KiB of
download.

`size -m` on the largest build:

```
__TEXT        3,719,168     __text        2,954,100
                            __const         566,212
                            __cstring        76,506
                            __eh_frame       51,424
                            __unwind_info    41,800
__DATA_CONST    196,608
```

### Reading

The realistic Phase 2 figure is **+1.3 to +1.6 MB of binary, +0.7 to +0.8 MB of download**, which
roughly **doubles** the `.dmg` — 1.47 MiB to about 2.15–2.26 MiB. Still an order of magnitude
inside the 10–15 MB the Tauri port was justified by, and still around 1/45th of Electron's
99,452,988. It is not a threshold failure. It is also not free, and it is the largest single
addition the project has made since the port.

The upper bound is genuinely an upper bound: the probe touched `Browser::launch`, `Page::execute`,
`Fetch`/`Network`/`Target` types, `Connection::submit_command` and `Browser::connect`. A Phase 2
that follows §1's advice — protocol types plus a raw connection, no `Browser` — should land below
these figures. **Task 12 must re-measure rather than carry this number forward.**

What ships from this task is the middle-left cell: chromiumoxide is declared in `Cargo.toml` and
referenced nowhere, so today's committed build costs **+160 bytes**.

## 3. The dictionary source — not Tracker Radar

### Method

Read the licence in the upstream repository, then sampled entries at a fixed revision.

- Repository: `https://github.com/duckduckgo/tracker-radar`
- Revision checked: **`6253f5a053513120c61ad8221dc30a0e2cdbfeb9`** (branch `main`, committed
  2026-07-27T18:28:58Z)
- Licence file: `https://raw.githubusercontent.com/duckduckgo/tracker-radar/6253f5a053513120c61ad8221dc30a0e2cdbfeb9/LICENSE`

GitHub's own licence detection reports `NOASSERTION`, which is why the file had to be read rather
than trusted.

### Question 1 — does the licence permit bundling the data in a closed-source commercial app?

**No.** The `LICENSE` file, in full:

> Copyright 2020 Duck Duck Go, Inc.
>
> Licensed under the CC BY-NC-SA 4.0 license, available at
> https://creativecommons.org/licenses/by-nc-sa/4.0/. Note that this license does not apply to any
> DuckDuckGo logos or marks that may be contained in this repo.

Two operative clauses in CC BY-NC-SA 4.0 decide it. The grant, §2(a)(1):

> reproduce and Share the Licensed Material, in whole or in part, for NonCommercial purposes only

with NonCommercial defined at §1(k) as

> not primarily intended for or directed towards commercial advantage or monetary compensation

and the ShareAlike condition, §3(b)(1):

> The Adapter's License You apply must be a Creative Commons license with the same License
> Elements, this version or later, or a BY-NC-SA Compatible License.

The NonCommercial term alone answers the question the brief asks. ShareAlike is a second,
independent bar: a bundled `vendors.json` derived from this data would be Adapted Material, and
shipping it would require licensing that material under BY-NC-SA. That is copyleft on the data, and
it lands on the same "no copyleft" rule already at issue elsewhere in this project.

The project's own licence being undecided does not change either answer. NonCommercial is about the
use, not about what Traccia is licensed as.

### Question 2 — does each entry carry an owner display name and at least one category?

**Yes, in every entry sampled.** Six domain files at the revision above, all with a non-empty
`owner.displayName` and a non-empty `categories` array:

| Entry | `owner.displayName` | `categories` |
|---|---|---|
| `google-analytics.com` | Google | Advertising, Analytics, Audience Measurement, Third-Party Analytics Marketing |
| `doubleclick.net` | Google | Ad Motivated Tracking, Advertising |
| `facebook.net` | Facebook | 12 categories |
| `cloudflare.com` | Cloudflare | Analytics, CDN, Embedded Content |
| `hotjar.com` | Hotjar | Analytics, Session Replay, Audience Measurement |
| `jquery.com` | OpenJS Foundation | CDN |
| `gstatic.com` | Google | CDN, Embedded Content |

The shape is right. The licence is not.

### Decision

**The dictionary is hand-written, 150–250 entries.** Task 1 is otherwise unchanged: the brief says
only the provenance of `vendors.json` moves, and its schema and every test are identical either
way. Tracker Radar may still be read as a *reference* when choosing which vendors to include and
what to call them — reading a page to inform a hand-written list is not reproducing the licensed
material — but no file from it is copied, transformed or shipped.

Two things Task 1 now inherits, and should not discover later:

- **The dictionary is a maintenance liability with no upstream.** 150–250 hand-written entries go
  stale, and there is no feed to refresh them from. The unknown-vendor path is therefore load-
  bearing, not a rare fallback, and the neutral copy rule ("not yet identified") is what carries
  it.
- **Attribution is not a workaround.** CC BY-NC-SA cannot be satisfied by crediting DuckDuckGo. The
  NonCommercial term is a use restriction, not an attribution requirement.

## 4. The PDF mechanism — the system print dialog

### The question, restated

Not whether macOS can make a PDF. Whether this app can open the print dialog at all, given that
`window.print()` is unreliable under WKWebView.

### First finding: it is not a WKWebView question first, it is a capability question

With the app exactly as it ships today, `window.print()` from the renderer produces:

```
[vite] (client) [Unhandled rejection] Unknown Error: webview.print not allowed.
Permissions associated with this command: core:webview:allow-print
```

Tauri v2 routes `window.print()` through its own IPC, and `src-tauri/capabilities/default.json`
grants `core:default` only. So the call rejects and nothing opens. Had the question been tested
without noticing this, the answer would have been a false "the dialog does not open" and Task 10
would have grown a Rust PDF writer it does not need.

### Second finding: with the capability granted, the dialog opens

Method, after temporarily adding `core:webview:allow-print` to the capability file:

- `npm run dev`, a temporary probe module in the renderer, results reported by rejecting a promise
  because Tauri forwards unhandled rejections to the dev server's stderr.
- The probe waits 25 s, emits a marker at 18 s, then calls `window.print()`.
- A compiled CoreGraphics helper listed every window owned by `traccia` (`CGWindowListCopyWindowInfo`
  with `.optionAll`, so windows on other Spaces are included) once a second for 45 s.

Result:

```
22:59:47  PRINTPROBE PRE-PRINT-MARK beats=157
22:59:47  total=6 onscreen=1 [4216:1280x820* … 4221:500x500]
22:59:54  total=7 onscreen=2 [4216:1280x820* … 4231:776x385*]     <- window.print() fires here
22:59:58  PRINTPROBE RESULT sync=returned-normally wall=2ms
          beatsBefore=188 beatsAfter=211 events=[beforeprint]
23:00:25  total=7 onscreen=2 [… 4231:776x385*]                    <- still open 31 s later
```

Five independent signals, agreeing:

1. **A new on-screen window owned by `traccia`, 776×385, appears in the same second `print()` is
   called** and did not exist in any of the eighteen samples before it.
2. It is still there 31 seconds later — a modal panel waiting for a user who is not there.
3. `beforeprint` fires; **`afterprint` never does**, which is what an open, unanswered print panel
   looks like.
4. The 100 ms heartbeat keeps ticking across the call (188 → 211 beats in ~4 s) and `print()`
   returns in 2 ms, matching wry's `print_operation.setCanSpawnSeparateThread(true)`.
5. macOS started `com.apple.PrintKit.PrinterTool` at 10:56 PM, the minute of the first successful
   print call.
6. **Control run:** identical build with the `window.print()` call commented out and nothing else
   changed. Forty-two consecutive samples over 42 s, every one of them
   `total=6 onscreen=1` — the 776×385 window never appears — and
   `events=[]`, so `beforeprint` never fires either:

   ```
   23:03:21  total=6 onscreen=1 [4255:1280x820* … 4260:500x500]
   23:03:23  PRINTPROBE PRE-PRINT-MARK beats=178
   23:03:34  PRINTPROBE RESULT sync=CONTROL-print-not-called wall=0ms events=[]
   23:04:07  total=6 onscreen=1 [4255:1280x820* … 4260:500x500]
   ```

   The window is caused by the print call, not by elapsed time.

The mechanism in wry 0.55.1 (`src/wkwebview/mod.rs:862`) confirms what was observed:
`NSPrintInfo.sharedPrintInfo()` → `webView.printOperationWithPrintInfo(_:)` →
`runOperationModalForWindow(_:delegate:didRunSelector:contextInfo:)`. That is a real
`NSPrintOperation`, whose panel carries macOS's built-in **PDF ▾ → Save as PDF**.

### Decision

**Task 10 takes the print-dialog branch: a print stylesheet and a button, and nothing else.** No
renderer→Rust path, no SVG serialisation, no Rust PDF writer.

With one addition Task 10 must not miss: **`src-tauri/capabilities/default.json` has to grant
`core:webview:allow-print`.** That file's own description currently reads "The renderer draws the
map. It holds no filesystem, shell, network or dialog capability." Granting print widens the
renderer's authority for the first time since the port, so it is a security-auditor gate, and the
description needs rewriting to stay true. The permission is narrow — it opens a print panel, it
does not read or write files, and the user still chooses the destination in a native panel — but it
should be granted deliberately and reviewed, not slipped in.

The capability grant made for this measurement has been reverted. Task 10 makes it for real.

### What this section could not determine

In the style of §4 of `2026-07-31-admission-audit.md`, named rather than left implied:

1. **The panel's contents were never seen.** The app opened on a different macOS Space, and this
   environment can neither capture a single window (`screencapture -l<id>` → "could not create
   image from window") nor drive System Events (`osascript` → error −25211, "not allowed assistive
   access"). The conclusion rests on the window-list evidence, the wry source, and the control run
   — not on a photograph of a print panel. Someone with a hand on the machine should open the app
   and look, once, before Task 10 ships. That is a five-second check that would upgrade this from
   *inferred with six agreeing signals* to *seen*.
2. **No one clicked "Save as PDF".** That the panel opens is measured. That the resulting PDF is
   legible — that the map's flat shapes and text survive the print stylesheet — is not, and cannot
   be until Task 10 has written the stylesheet and there is a map to print.
3. **Measured under the dev profile, not the shipped release build.** wry's print path does not
   branch on profile, so this is expected to carry; it was not verified. Cheap to check when Task
   10 builds.
4. **macOS only.** Windows was not tested — this Mac cannot build for Windows, as the CDP spike's
   F8 established. wry's Windows print path is a different implementation, and the plan should not
   assume this answer transfers.

## What changes in the plan

1. **Task 1** — the dictionary is hand-written. Schema and tests unchanged; provenance changes, and
   the unknown-vendor path becomes load-bearing rather than a rare fallback.
2. **Task 7** — `chromiumoxide` is a protocol vocabulary, not the interception loop. Do not let
   `Browser` own the attach/resume sequence; F2 cannot be satisfied through it. Assert the
   recursive auto-attach rather than assuming the crate reapplies it per session.
3. **Task 10** — the print dialog branch. Add `core:webview:allow-print` to the capability file, and
   send that change through the security-auditor gate.
4. **Task 12** — re-measure. The +160 bytes in today's build is a stripping artefact; the real
   figure arrives with Task 7 and lands somewhere under +1.6 MB of binary.
5. **Open, not decided here** — whether to move the pin to 0.9.1, and whether to accept
   `reqwest`/`hyper` in the tree at all. Both are Phase 2's, and both are named in
   `src-tauri/Cargo.toml` so they cannot be forgotten.
