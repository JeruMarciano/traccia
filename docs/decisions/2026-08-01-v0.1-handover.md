## 1. What this release is

A scan of a URL the user explicitly types drives a real, unmodified-binary Chrome (or Edge, where
present) through an ephemeral profile, behind a per-scan loopback CONNECT proxy that admits only
the scan's own origin and its subdomains. Everything the proxy denies is recorded; everything it
allows is recorded; the scan fails rather than reporting clean if the ledger ever drops a record.
The result is folded into the existing project/place/purpose model, printed with an explicit
statement of what a scan cannot see, and the browser profile is removed afterwards.

## 3. Named `#[ignore]`d tests, and why

### 3.1 `no_dns_query_leaves_the_machine` — `src-tauri/tests/egress.rs`

Ignored because it binds loopback UDP port 53, which needs root (or the Windows equivalent) — a
privilege this test suite does not assume the runner has. The suite also deliberately does not
repoint the OS resolver to make an unprivileged port meaningful, because that would be a side
effect on the host machine outside what a test is allowed to do.

**Consequence, stated plainly: the no-DNS property is asserted nowhere at runtime, in CI or
otherwise.** It is enforced by browser flags (`--disable-quic`, `--webrtc-ip-handling-policy=
disable_non_proxied_udp`, plus the disable-background-networking family) verified by reading the
Chrome 151 binary's own switch table (Task 6's audit), not by an executed test that watches for a
DNS packet leaving the process. Running this test manually with elevated privileges before a
release, on each target OS, is the only way this claim has ever been checked end to end.

### 3.2 No other `#[ignore]` exists in the tree

`grep -rn "#\[ignore" src-tauri/` (broad enough to match the real attribute, `#[ignore = "..."]`,
not just a bare `#[ignore]`) returns only this one test's attribute plus doc comments referencing
itself. There is no second ignored test anywhere in the Rust or TypeScript suites.

## 4. The `file://` remote-authority requirement — specified, not enforced

`docs/decisions/2026-07-31-admission-audit.md` §1 named this the successor to the predecessor
guard's `file://`/SMB defect and carried it forward as a Phase-2 requirement, because an HTTP
CONNECT proxy structurally cannot see an SMB fetch — the proxy is not, and cannot be, the
enforcement point.

Task 6 wrote `browser::url_is_permitted` to specify the rule precisely (deny a `file://` URL
naming a remote authority, allow the local/hostless forms, allow the other local schemes) and
covered it with tests. **It is, by its own doc comment, an unwired spec: nothing in the running
scan pipeline calls it.** `scan.rs` says so directly at its own admission-guard comment:
`browser::url_is_permitted` is an unwired spec, so there is no second gate — the residual risk is
judged low because Chromium refuses to load a `file://` subresource from an `http(s)` document in
the first place, but that is a property of Chromium's own behaviour, observed and trusted, not a
property this codebase enforces or tests against a real page. `tests/egress.rs`'s own limitation
comment records the same gap and does not exercise any `file://` scan target.

A passing `url_is_permitted` test proves the function is correct. It does not prove the function
runs. Anyone reading a green test suite and concluding this requirement is enforced would be
wrong, and this section exists so that reading does not happen.

## 5. The `scan_origins` mutex — fail-closed by construction, not by test

`scan_origins.lock().map(...).unwrap_or_default()` degrades a poisoned mutex to an empty origin
list, which `admission::decide` treats as `NoScanRunning` — deny everything. This is correct by
inspection and was reviewed as such in the admission audit (§4 item 4 there, carried forward
unchanged here): deliberately poisoning a mutex from a test requires a panicking lock holder, and
this crate ships `panic = "abort"` in `[profile.release]`, under which a panicking test process
aborts rather than unwinding into a recoverable state a test harness could observe. No test in
this codebase poisons the mutex. The fail-closed behaviour of a poisoned `scan_origins` lock
remains **structural, asserted by the type of `unwrap_or_default()`, never exercised by a test
that actually poisons it.**

## 6. The app's own webview — not behind the proxy

The proxy governs only the Chrome/Edge instance a scan launches. Traccia's own Tauri webview
(the UI the user clicks around in) never passes through it and was never intended to: it loads
`ipc:` and the bundled `http://ipc.localhost` frontend only. It is defended by two other
mechanisms instead:

- **CSP**, set in `src-tauri/tauri.conf.json`: `default-src 'self'; style-src 'self'
  'unsafe-inline'; img-src 'self' data:; connect-src ipc: http://ipc.localhost; base-uri 'none';
  form-action 'none'; object-src 'none'; frame-src 'none'`. No remote origin is reachable from
  script, style, image, or navigation.
- **A bundle asserted to carry no remote references**, checked by `tests/build/
  noRemoteAssets.test.ts` and `tests/build/bundleClean.test.ts` against the built output, not
  just the source.

This is a different, and weaker, kind of guarantee than the proxy's: it is "nothing in the bundle
points off-machine", checked statically, rather than "every attempt was observed and admitted or
denied", checked dynamically. It has held for every task in this plan but it is not the same
promise the scan itself makes about the site it visits.

## 7. Consolidated open items (carried from the ledger, Tasks 5–12)

Everything below was open at the end of its originating task and remains open at the end of this
one. None of it blocked a security audit; all of it is disclosed rather than hidden.

- **DNS sensor `#[ignore]`d, no-DNS property unasserted at runtime.** §3.1 above.
- **`KNOWN_DENIED_BROWSER_SERVICE_HOSTS` — attempted-and-denied, no verified off-switch in Chrome
  151.** GAIA account listing (`accounts.google.com`), GCM device checkin
  (`android.clients.google.com`), `www.gstatic.com`, and a search-preconnect remnant
  (`www.google.com`) are each contacted by the browser's own background subsystems during a scan
  and each denied by the proxy — nothing reaches the network — but Task 11's bounded, evidence-
  based search found no Chrome 151 switch that suppresses the *attempt* itself for any of the
  four. `gvt1`/`mtalk`/`clients2.google.com` are verified absent under the current flag set; the
  absence claim is asymmetric across the two groups and disclosed as such in `egress.rs`'s own
  comment.
- **Early-FIN behaviour is unexercised against a real origin server.** The proxy's plain-HTTP path
  reads to EOF against a well-behaved fixture only. If a real nginx/Apache/IIS/CDN origin treats a
  half-close as an aborted request, a scan of that site would render blank rather than erroring —
  silent failure, not caught by any test in this suite. Flagged from Task 5 onward as a functional
  risk that only a live scan against a real site can retire.
- **Admission-audit §1's `file://`/SMB carry-forward is still open**, as detailed in §4 above:
  `url_is_permitted` is an unwired spec, stated plainly rather than implied by a passing test.
- **QUIC/UDP/mDNS are invisible to the proxy ledger by construction.** The ledger only ever learns
  about a connection that reached the proxy's TCP listener; it is not evidence that no packet left
  the machine by another path. Mitigated by browser flags (verified against the Chrome 151
  binary), not observed by any test.
- **Edge is entirely unverified.** Task 4 discovers it; Task 6's flag verification and Task 11's
  live egress checks were run against Chrome only, because that is what was installed in the
  execution environment. Nothing about Edge's actual behaviour — flag names, background traffic,
  teardown — has been checked.
- **Chrome's descendant processes (renderer, GPU, zygote) are not killed by `kill_and_wait`.** It
  kills the child PID only. Chrome's own process-tree teardown is relied on, not verified by this
  codebase killing each descendant itself.
- **`scan_origins` mutex poisoning is untested.** §5 above.
- **The app webview is not behind the proxy**, defended by CSP and a bundle asserted to carry no
  remote references. §6 above.
- **Windows bundle size is pending CI.** Task 12 recorded the macOS `.dmg` (1,647,339 bytes,
  60.4x smaller than the Electron comparison) by direct measurement; the Windows artefact
  (`bundle (windows-latest)` / `traccia-windows-latest`) was named but not measured, because no
  Windows runner was available in this execution environment.
- **No startup sweep of stale `traccia-scan-*` profile dirs.** `panic = "abort"` means a panic
  mid-scan leaves the ephemeral, cookie-holding, `0700`-permissioned profile directory behind
  indefinitely — the browser and proxy are both dead with it, so it cannot reach the network from
  there, but it is still a leftover credential store on disk with no cleanup path on the next
  launch. Documented in `browser.rs`; no sweep exists.
- **Print-by-eye and a real-site scan were never performed.** Every task from 9 through 13 that
  called for visually confirming a printed sheet, or running `npm run dev` against a real client
  site to confirm "stop actually stops" and the early-FIN risk above, was merged into this single
  live-verification obligation, because **no GUI is available in this execution environment.**
  Nothing in this release has been seen running by a human. This is the largest single gap in the
  verification record and it applies across Tasks 5, 9, 10 and 11 at once, not to any one of them.
- **A reopened project prints with no incompleteness sentence, even when the original scan had
  gaps.** Gaps are computed on demand and never stored in the project file, by design; `lastScan`
  is cleared on Open, by design. Together, printing a project that was reopened rather than
  freshly scanned is quieter than the truth in that one case — the printed sheet says nothing about
  incompleteness where a still-open session would have. Not a defect in either design decision on
  its own, but a gap in their combination that this release does not close.

## 10. Where this release under-delivered against the plan

Written to be read plainly rather than softened.

- **No live verification exists for any of the behaviour that can only be seen live.** Stop-
  actually-stops, the early-FIN risk, print-by-eye, a real scan against a real client site — the
  plan called for all four and none happened, because the execution environment has no GUI and no
  network egress to a real site was exercised end-to-end by a human watching it. This is not a
  small gap; it means the release's central promise — "map where this organisation's data goes" —
  has been checked by construction and by audit, never once by actually doing it against a site
  that was not the test fixture.
- **`file://` enforcement is specified but not wired**, per §4. The plan's own Task 6 called this
  the weakest point in the plan at the time it was written, anticipating exactly this outcome
  rather than being surprised by it — but it shipped unwired regardless, and the residual-risk
  argument for shipping it that way rests on trusting Chromium's own behaviour rather than on
  anything this codebase verifies.
- **Edge support is entirely unverified**, despite Task 4 discovering it and the plan naming it
  as a supported browser. Everything downstream of discovery — flags, background traffic,
  teardown — was checked against Chrome only.
- **Windows is unmeasured for size** and untested for the platform-specific paths named in the
  ledger (candidate-path account-name stripping, profile-directory permission semantics, teardown
  failure modes) beyond what unit tests can exercise without the OS itself.
- **The no-DNS property, asserted in the spec as a hard requirement, is unverified at runtime.**
  It rests on flag-table verification against one pinned Chrome binary and on an `#[ignore]`d test
  nobody has run with the privilege it needs.

None of the above changes the audit verdicts already recorded — every security gate this plan
required (Tasks 5, 6, 7, 8, 10, 11) reached PASS before its task was called complete, several
after a BLOCK-and-fix cycle with the fix independently re-verified. What this section adds is the
distinction between "audited and passed" and "seen working", which this release has the first of
and not the second.
